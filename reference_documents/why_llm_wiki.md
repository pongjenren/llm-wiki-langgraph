針對企業內部部署 LLM-wiki 這種知識庫模式,以下是我認為的主要優缺點:

## 優點

**1. 知識隨時間「複利式」累積,而非每次重新推導**
傳統 RAG 每次查詢都要重新檢索、重新拼湊上下文,LLM-wiki 把「理解」的工作提前做好——新文件進來時就更新既有頁面、標記矛盾、強化交叉引用。查詢時直接讀已經整理好的知識,速度快、也更一致。

**2. 可讀、可審查、可版控**
輸出是純 markdown,不是黑盒子的向量索引。這代表:
- 可以直接用 Git 做版本控制,追蹤「知識庫在某個時間點長什麼樣子」
- 人可以肉眼檢查、編輯、糾正 LLM 寫錯的內容
- 離開某個 vendor 的向量資料庫依賴,資料可攜性高

**3. 跨文件的推理能力更強**
因為 wiki 頁面之間有明確的交叉連結(entity page、concept page 互相引用),查詢時 LLM 能看到「全局脈絡」,而不是像 RAG 那樣只拿到幾個孤立的 chunk。這對「這個決策跟三個月前那次討論的政策是否衝突」這類跨時間、跨文件的問題特別有幫助。

**4. 維護新知識的成本被攤提**
矛盾偵測、孤立頁面、缺頁概念的 lint 機制,讓知識庫不會像傳統 wiki 一樣隨時間腐化——但維護的苦工是 LLM 做,不是人。

## 缺點

**1. Ingest 成本會隨語料量非線性增長**
每次加入新文件不是單純「embedding 後丟進向量庫」,而是要讀取、萃取、比對既有頁面、決定要新增/更新哪些頁面。當 wiki 已經很龐大時,LLM 需要吞下的既有 context 也會變大,token 成本跟延遲都會上升——這也是為什麼有些實作(如 wiki-llm)選擇用 BM25 而非向量檢索來輔助定位相關頁面。

**2. 一致性與正確性高度依賴 LLM 品質與 schema 設計**
如果沒有嚴謹的 schema(CLAUDE.md/AGENTS.md)與型別化契約,LLM 寫出來的頁面格式會逐漸漂移——標題層級不一致、連結斷掉、同一實體被建立成兩個重複頁面(尤其在多語言環境,例如中英文夾雜的企業場景更容易出現)。

**3. 需要人力監督,尤其早期**
前 10-20 次 ingest 通常需要密切檢查——確認概念抽取是否正確、連結是否有意義、矛盾標記是否恰當。企業場景如果資料來源龐雜(會議記錄、Slack、合約、客戶通話),初期監督成本不低。

**4. 敏感資訊與權限控管是額外課題**
企業內部知識庫常涉及不同權限層級(人資、財務、客戶資料),但 LLM-wiki 這個模式本身沒有內建的存取控制機制——需要額外設計誰能看到哪些頁面,而不是像傳統 RAG 系統那樣可以在檢索層做權限過濾。

**5. 「重新編譯」的成本**
如果 schema 設計錯了,或想大幅調整 wiki 的組織方式,理論上需要從原始來源重新編譯整個 wiki——這對已經累積數千份文件的企業知識庫,可能是一筆不小的重跑成本。

## 一個實務建議
企業場景我會建議把 **raw sources 保持不可變、有明確保留策略**,並且及早投入時間設計好 schema 與型別化的 ingest pipeline(如同你上一個問題提到的 LangGraph 方案),把「lint 頻率」跟「人工審核關卡」設計進流程,而不是等 wiki 已經很大才發現一致性問題。
